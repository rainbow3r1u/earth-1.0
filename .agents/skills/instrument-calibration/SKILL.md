## 0. 为什么需要"标定"而不是"配置一次就完事"

GPU 回测仪器的可信度会**静默腐烂** —— 它不会报错, 只会给你一个看起来很正常但**偏高**的数字。

**实证（2026-09-13）**：缓存里 `dim13-16`（= r2 / residual / rsi7 / rsi14，"对BTC残差传感器"的核心几维）
吃到了**样本日当天收盘价** → 一日前视。后果：
- 复现生产预测的 Spearman 只有 **0.20**（top10 重合 0/10，生产自身重训是 5/10）
- 概率**饱和到 96%**（生产 87.9%）
- **GPU 历史所有绝对水位全部偏高**（含"干净基线 16.81"、Sharpe 17.29/25 等）

**它唯一暴露自己的方式是"概率饱和"这个肉眼签名** —— 而这正是 8/01 幽灵问题被发现的同一个签名。
所以规程必须变成**每次开跑前的动作**，不能只写在文档里等"记得"。

## 1. 连接信息（GPU 的 IP / 端口 / 密码每次都变）

**脚本从不硬编码连接信息**，按此顺序解析：

```
① 环境变量  GPU_HOST / GPU_PORT / GPU_USER / GPU_PASS
② 本地配置  ~/.gpu_conn   (JSON, 自动 chmod 600, 不入 git)
③ 都没有    → 报错并给出下面的两条命令
```

**更新连接（二选一）**：

```bash
# A. 写进本地配置(推荐, 一次写入后续免输)
python3 scripts/instrument_calibrate.py --set-conn HOST:PORT
#    → 会交互式询问密码(不落 shell 历史), 写入 ~/.gpu_conn

# B. 一次性临时用(不落盘)
export GPU_HOST=<当前IP> GPU_PORT=<当前端口> GPU_USER=linux GPU_PASS='***'
python3 scripts/instrument_calibrate.py --check
```

> ⚠️ **不要**把连接信息写进仓库任何文件、脚本、文档或 AGENTS.md —— 文档里的端口必然过期
> （现存 `docs/gpu_server_connection.md` 写的是 22160、AGENTS §7.6 写的是 24127，2026-09-13 实际是 22172，全都不一致）。
> **向用户索取当前连接**是唯一可靠来源。

## 3. 七条规程 → 判据（AGENTS §8.2 的可执行版）

| # | 规程 | 判据 | 本脚本 |
|---|---|---|---|
| 1 | **数据同源** | 远端 `sent / chain_tvl / liq / dominance` 加载天数与本地**逐项相等**（本地参照 128 / 3272 / 96 / 482） | `--full` ⑤ |
| 2 | **特征同源** | 取任一共同日重建该日特征 vs 生产 `pred_feats_*.npz`：**逐币相关 ≈1.0** 且**无整块全零维** | 手动（判据见下） |
| 3 | **仪器标定（最关键）** | **概率向量 Spearman ≥ 0.90**（对照生产 `pred_*.json` 的 `all_long`）**且概率不饱和** | 手动 + §4 签名 |
| 4 | **结算标定** | 自建结算 vs 影子档**逐笔一致率 ≥90%**（正确口径：入场=T0开盘, 扫T0..T2的low, 平T2开盘；错用 T+1 开盘会掉到 66.9%） | `--settlement` ④ |
| 5 | **显式传参** | `TOP10_LONG=1` / `SOUP=1` / `SL_PCT=8` / `VOLRAW_FEATS=1` / `FUND_FEATS=1`（引擎默认全是 0，不传就是另一套结构） | `--check` ③ |
| 6 | **增量落盘** | SOUP 状态纯内存不落盘 → walk-forward **不可中断续跑**；长跑必须每 5 天写盘 | 手动确认 |
| 7 | **严格串行** | 同一时间只跑一个 GPU 实验（本脚本会检查；`nvidia_gpu_exporter` 是监控守护，不算任务） | `--check` ② |

### ⚠️ 2026-09-13 对第 3 条判据的修正

> **不要再用"选币重合度 >80%"当仪器合格判据。**
> 原因：top10 是**刀刃**（第 10/11 名的概率差常 <1pp）—— **生产模型自己重训一次，top10 也只重合 5/10**。
> 所以选币重合度低 ≠ 仪器坏。
> **正确判据 = 概率向量 Spearman ≥0.90 + 概率不饱和。**

## 4. 头号诊断签名：概率饱和 = 前视/泄漏

```
复现模型的 max_prob 明显高于生产(如 96% vs 88%) → 立刻查"特征是否用到了样本日当天的 bar"
```

**检测方法（可复用，2026-09-13 用它定位了 dim13-16）**：
1. **篡改检验**：把样本日 D 的那根 K 线人为改掉（收盘×3），重建该日特征 → **若特征变化，说明用到了当天 bar**
2. **全宇宙篡改**：改掉当日所有币的 bar 再测一遍 → 可区分"价格类特征泄漏"与"板块热度类泄漏"（后者当时实测**不泄漏**）
3. **定位维名**：按 `assemble_feature_vec` 的参数顺序反推泄漏维属于哪个特征族
4. **口径对照**：把该维与生产 `pred_feats_*.npz` 逐币比对，确定生产到底用的是哪个时点（实测 = **前一日收盘**，corr 0.816 / 平均差 0.042）

**机制（为什么生产没泄漏）**：生产 **08:05** 构建时**当天 bar 尚不存在**（07:30 采集只到前一日）→ 那几维用的是前一日数据；
而 GPU 从**全量历史K线**构建 → 当天 bar 在 → 吃到当天收盘价。

## 5. 影响面（谁受损、谁安全）—— 每次汇报仪器结论时必须带上

| 对象 | 状态 |
|---|---|
| **生产实盘** | ✅ 安全（早上构建时当天 bar 不存在，从未泄漏） |
| GPU 回测**绝对**水位 | ❌ 全部偏高（**铁律4「回测水位不可作生产预期」由此有了具体机制**） |
| GPU 回测**相对** A/B | ⚠️ 两臂同等泄漏 → 仍可用于排序 |
| 用"生产存档选币 + K线"做的分析 | ✅ 不受影响（金矿格归因/SL 网格/抓尾 lift/8-3前后对比都属于这类） |

**不可复原的边界**：外部数据文件每日被采集器重写（`last_added_date` 即当日），历史时点值不可回捞
→ **逐位复现历史预测物理上不可能**；"同一个模型"的准确表述 = **同一条流水线 + 不同时点的数据**。
